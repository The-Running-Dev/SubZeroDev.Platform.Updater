# Release and host integration

## Library

Run `scripts/Test-Package.ps1` on Windows with .NET 10. It runs tests and API/XML analyzers, creates the NuGet and symbols packages, validates metadata, and restores WPF and WinUI consumers using a new empty package cache. The package is UI-independent; samples take a PackageReference and receive Velopack transitively for the mandatory bootstrap call.

The library is MIT licensed (`LICENSE`, `PackageLicenseExpression`); `Test-Package.ps1` checks the package declares it. For each release, increment Directory.Build.props and the samples' central package version together, move reviewed API entries from PublicAPI.Unshipped.txt to PublicAPI.Shipped.txt, update CHANGELOG.md, and tag the tested commit (`v0.1.0` first). The Publish NuGet workflow checks the tag and LICENSE, tests the package, then publishes with NuGet trusted publishing: it exchanges the workflow's OIDC token for a short-lived API key, so no long-lived key is stored. One-time setup: on nuget.org add a trusted publishing policy for repository `The-Running-Dev/SubZeroDev.Platform.Updater`, workflow `publish.yml`, environment `nuget`; in GitHub create the `nuget` environment (with required reviewers) and set its `NUGET_USER` variable to the nuget.org account that owns the policy. Missing setup stops publication; it never substitutes a private package feed. SourceLink uses the SDK's GitHub provider; symbols are in the snupkg.

## Application distributions

Pin both Velopack runtime and vpk to **1.2.161**. `scripts/Pack-Application.ps1` accepts the project, application ID, main executable, version, notes, and a fresh output directory. It produces a self-contained win-x64 publish and calls the verified `vpk pack --msi --instLocation PerUser` flags. The portable archive contains the root launcher, Update.exe, `.portable`, and `current`; never redistribute only `current`. The stable root launcher is **AppId.exe**, which need not equal the main executable's filename.

Each new release has its own full package and feed. Stable is `vX.Y.Z` / `win-stable`; preview is `vX.Y.Z-preview.N` / `win-preview`, marked prerelease. Do not reuse old cumulative channel feeds under a new GitHub release: every entry must match the release tag and have its corresponding asset in that release. Preview clients query both streams and choose the greatest version above the installed one. Drafts and legacy releases without feeds are ignored. Clients list up to three pages of 100 releases per stream and walk their feeds newest first until one passes validation. Five malformed feeds no longer hide a valid older release. The worst case is three REST listing requests and 300 GitHub asset downloads per stream; a healthy stream needs one feed download. Releases outside that 300-release window remain outside the search. A deadline of two minutes, or twice `NetworkTimeout` when that is longer, covers the entire check across both channels, including signatures. Exhausting it reports network unavailability, never up-to-date; cancellation and individual request timeouts still apply. Metadata requests and retries are bounded; 403/429 are actionable rate-limit outcomes.

### Package signing key

Create the publisher key once with `scripts/New-SigningKey.ps1 -PrivateKeyPath <path outside the repository>`. It prints the public key: embed that in the application as `UpdaterOptions.PackageSigningKey`. When `UPDATER_PACKAGE_SIGNING_KEY` holds the private PEM, `Pack-Application.ps1` writes `<package>.sig` for every full package before SHA256SUMS; without it, it warns and the release cannot be installed by clients that pin a key. Production publication requires the public key (or its file) as `Publish-Release.ps1 -PackageSigningKey`; missing keys or invalid signatures stop before any GitHub command. Unsigned packaging remains available for local development and CI format checks. The WPF and WinUI samples embed `-p:UpdaterPackageSigningKey=<base64 SubjectPublicKeyInfo>` at build time and require it for publishing; their updater refuses to start without it except for the explicit `UPDATER_SAMPLE_SMOKE` check. The test probe uses an ephemeral key pinned by its test harness. This repository does not configure other deployed applications; their owners must embed the publisher key themselves.

The key is only useful if release write access alone cannot use it. Store it in a separate protected environment with required reviewers (or offline), never alongside the token that writes GitHub releases, and never in either repository. Clients without a key fall back to per-release SHA-256 only, and their `InstallAutomatically` consent prompts instead of installing silently. To rotate, ship an application version that pins the new public key while releases are still signed with the old key, then switch signing once that version is widely installed. Keep the bridge release available for clients still pinning the old key. If the old private key is lost, recover its protected backup or distribute a new installer through a trusted external channel: an old-key client cannot authenticate a bridge signed only by the new key. A leaked key requires incident recovery; an attacker with release write access can reach old-key clients until they migrate.

`scripts/Publish-Release.ps1` checks local hashes and required assets, creates a draft, uploads all assets, checks every remote asset's name, size and SHA-256 digest (downloading any asset GitHub reports without a digest), then publishes. Initialize the binary repository with a README first; GitHub cannot publish tags in an empty repository. It refuses to replace existing releases, and stops unless GitHub definitely reports the tag as absent. An interrupted draft requires inspection, never blind overwrite. Use a repository-scoped token with Contents write for cross-repository workflow publication. Desktop clients have no tokens.

Windows Authenticode signing is separate from the mandatory publisher package signature. No Windows code-signing credential is assumed. Supply a signing identity through a protected environment only when one is configured: `VELOPACK_AZURE_SIGN_FILE` (path to an Azure Trusted Signing metadata file; credentials come from the environment), or `VELOPACK_SIGN_TEMPLATE` (a custom signing command that reads its secrets from the environment). `VELOPACK_SIGN_PARAMS` still works but is used last and warns, because signtool arguments, including any certificate password, appear on the process command line. Artifacts without Authenticode signatures remain usable but may show Windows reputation warnings. Do not describe them as signed.

## Host responsibilities

Call `VelopackApp.Build().Run()` directly at the beginning of synchronous Main. After UI initialization create the client and observe its startup task. Render notes as text, marshal events to the UI, keep manual results visible, and preserve the exact candidate presented for Install. A channel change affects subsequent checks; it does not replace the displayed candidate.

The restart coordinator returns Defer while editors or critical operations are active. For Ready, stop work, dispose tray/windows and release the instance guard before returning. Exit normally after Completed; Velopack waits for the process to exit. Keep the UI dispatcher running until the coordinator has finished; never synchronously wait for it on that dispatcher. Dispose the client on ordinary quit to cancel outstanding work. A staged package may be applied by the next Velopack bootstrap after a user-approved download.

Settings belong outside `current`. Atomically persisted updater.json contains schema version, automatic-check flag, channel, consent, network timestamps, per-version deferral and the version a scheduled restart is expected to start. No app config schema migration is required. Defaults are automatic checks, Stable, and confirmation each time. Later defers only that version for 24 hours. Consent is saved only with explicit Install; it can be revoked independently. Offline corner operation is unaffected.

## Package exercises

`tests/UpdaterProbe` is a test-only executable. Its external control JSON selects a target, app ID, data directory and optional local feed. `UPDATER_PROBE_CONTROL` points to that JSON. It records package version, compiled binary version, process path and updater states, installs the selected version, exits gracefully, and records completion after real relaunch. A null feed uses the production public-GitHub provider, without a token; a local feed directory is served through a fake GitHub (`FakeGithub` in the probe) so the production `ValidatedGithubSource`, downloader, redirect allowlist and signature lookup all run. Use distinct install directories and retain data outside them.

For the actual HotCorners local-feed exercise only, build the library with `-p:UpdaterLocalValidation=true` (HotCorners keeps its own `UPDATER_LOCAL_VALIDATION` define): the library then reads UPDATER_VALIDATION_FEED and HotCorners requires HOTCORNERS_VALIDATION_DATA. The property stamps the package `X.Y.Z-local-validation`; the build fails if the constant is defined any other way or that suffix is overridden, and the Publish NuGet workflow refuses such packages. These branches are absent from normal release binaries. Keep validation packages in a separate feed/cache and never upload them as product releases. See validation.md for recorded results and remaining external gates.
